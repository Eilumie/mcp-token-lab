# Reproducible experiment: full schemas vs progressive loading

This is a **constructed simulation**, not measured MCP execution, a vendor benchmark or the application's default opening template. The app currently opens the first of five built-in templates, which uses 120 tools and three plans; this publication fixture deliberately uses 100 tools and two plans for a readable comparison.

## Run and verify

From the repository root, after `pnpm install --frozen-lockfile`, with Node 22.12+:

```sh
node scripts/reproduce-example.mjs --check
```

This runs `simulate()` from `src/session-report.js` through the real `Session` engine and compares four committed outputs byte-for-byte. It makes no model or MCP network requests. To intentionally regenerate the outputs:

```sh
node scripts/reproduce-example.mjs
```

Review changes; do not accept a new baseline simply to hide an unexplained mismatch. Run `pnpm test` when the accounting model changes. Floating point values in outputs are rounded to six decimal places; source engine totals retain JavaScript precision.

## Fixed assumptions

| Parameter | Value |
|---|---:|
| User turns / tools / skills | 100 / 100 / 30 |
| Mean tools / skills per turn | 1.5 / 0.33 |
| Agent prompt | 4K |
| Index per skill / tool | 0.1K / 0.013K |
| Schema per tool | 0.51K |
| User message | 0.1K |
| Detail per skill / result per tool | 3K / 3K |
| Skill plan / schema plan / tool plan output | 0.1K / 0.1K / 0.3K |
| Final response | 1K |
| Expected prefix-cache hit rate | 0.9 in JSON; 90% in UI |
| Compression trigger | Context >=100K after a completed turn |
| Retained turns / summary | 2 / 4K |
| Durations | Disabled; no timing claim |
| Baseline | Full schemas, manually selected |
| USD / 1M cached input, fresh input, output | **0.20 / 2.00 / 8.00, synthetic** |

Every step executes each turn; no probabilistic triggers. Both plans inherit shared parameters and custom rates. Progressive loading begins with 8.3K (4K prompt + 3K skills index + 1.3K tools index). Full schemas add 51K of definitions, starting at 59.3K. The progressive flow adds schema planning and loading each turn; full schemas omit those two steps. Both retain the same skill and tool-result assumptions. See the complete JSON for step order.

## Results and what they mean

| Metric | Progressive loading | Full schemas |
|---|---:|---:|
| Input K, cached + fresh | 26,497.64 | 29,339.50 |
| Cached input K | 22,982.175 | 25,388.982 |
| Fresh input K | 3,515.465 | 3,950.518 |
| Output K | 186 | 236 |
| Requests, including compression | 409 | 324 |
| Compressions | 9 | 24 |
| Estimated USD at synthetic rates | 13.115365 | 14.866832 |

Cumulative input counts every request's input, including repeated context and compression requests. It excludes output and is not peak input or final context. The chart's K scale means 30,000K = 30 million tokens. Compression can reduce later request sizes but cannot make cumulative input decrease. No curve smoothing or fitted values are used.

The larger initial full-schema context reduces available room before the 100K compression threshold. Progressive loading has an extra request each normal turn; its smaller prefix does not automatically mean less total work. Output includes the extra summaries and planning steps. No task-quality equivalence is established.

## Counterexample and sensitivity

Change **only** the indicated global field; all other values remain fixed. Each row is regenerated by the script.

| Tools | Progressive input K | Full-schema input K | Progressive estimated USD | Full-schema estimated USD |
|---|---:|---:|---:|---:|
| 10 | 26,019.110 | 19,618.990 | 12.933524 | 10.256125 |
| 100 | 26,497.640 | 29,339.500 | 13.115365 | 14.866832 |
| 300 | 26,248.445 | 75,234.350 | 13.084601 | 37.424890 |

At 10 tools, full schemas are cheaper under these assumptions. At 300 tools, the full initial context already exceeds the trigger; the engine still waits until turn end to check compression. That case illustrates an accounting boundary, not evidence that an actual model would accept that request. Compression timing also explains why the progressive input total is not monotonically increasing here.

| Expected prefix hit rate, with 100 tools | Progressive estimated USD | Full-schema estimated USD |
|---|---:|---:|
| 10% | 49.886845 | 55.489204 |
| 50% | 31.501105 | 35.178018 |
| 90% | 13.115365 | 14.866832 |

Changing this rate affects the hit/miss allocation and estimated cost, not input volume. It does not represent a measured cache-hit distribution. No guaranteed percentage reduction should be derived from these examples.
